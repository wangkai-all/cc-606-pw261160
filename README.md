# 青禾夜市 · 摊位利用率分析台

按票入账、登记表驱动的本地夜市摊位利用率分析。全部计算在本地完成，只使用 Node.js 内置模块（无第三方依赖）。

## 运行

```bash
node server.js            # 默认端口 3000
PORT=43117 node server.js # 指定端口
```

服务只绑定 `127.0.0.1`，启动后访问 `http://127.0.0.1:<PORT>/`。

```bash
node --test               # 46 个用例，覆盖正常与异常路径
```

## 页面上的三个动作

| 按钮 | 实际做的事 |
| --- | --- |
| 「运行原营业分析」 | 按登记营业时间逐场求交，算出可经营分母、票数、每小时票量与逐摊逐场明细 |
| 「补交临时停业」 | 校验并落库一条停业登记，随后回查受影响的场次和落在停业窗口内的票据归属 |
| 「查看可用时段分母」 | 展示分母的构成：每个摊位每晚的可用分段、被停业切掉的时长 |

业务结果区 `#result` 带有 `data-evidence-result`（以及 `data-result-kind`）属性，每次操作后由真实计算结果重写，例如：

```
ANALYSIS|2026-11-16..2026-11-25|sessions=9|stallNights=62|available=311.5h|closed=7.0h|tickets=594|unallocated=3|closures=4
AVAILABILITY|2026-11-16..2026-11-25|rows=62|available=311.5h|closed=7.0h
```

页面上没有写死的业务数字——所有值都来自 `/api/analysis`、`/api/availability`、`/api/closures/backfill` 的响应。

## 核心设计

### 1. 实时区间求交，不做预汇总

可经营时长 = `摊位登记窗口 ∩ 市场营业时段 − 当晚停业登记`，每次分析都用 `lib/time.js` 的
`intersect` / `merge` / `subtractAll` 重算，没有缓存任何按场次或按摊位的汇总值。

这样做的代价与收益：分析时多算一次，但补录停业后**不需要回滚或重算历史汇总**——重新跑一遍
`analyse()` 即可，`beforeDigest` / `afterDigest` 是同一份代码对同一批数据前后两次真实运行的结果，
`availabilityDelta` 因此是精确值（不是估算）。如果改成预汇总，任何一次补录都要找到受影响的汇总行
并做增量回滚，跨零点、区域停业、推导停业叠加时极易漏算。

### 2. 跨零点不按日期裂场

营业日以**开市日期**命名。`close <= open` 表示次日收市（`00:00` 即 24:00），一晚仍然只有一场：

- 周五 18:00–00:30 生成一个 `nightKey = 周五日期` 的场次，`crossesMidnight = true`；
   不会因为日历翻页多出一场周六凌晨的营业日。
- 票据先找"包含该时刻的场次"，所以 11-21 00:15 的小票归属 11-20 开市的营业日，
  依据标记为 `clock-after-midnight`；带显式 `sessionId` 的票据以登记为准（即使时刻落在营业时间外，
  也会入账并被标记为 off-clock，不计入可经营票数）。

### 3. 票数的两个口径

- `ticketCount`：归属到该场次的全部票据（用于回查"同一交易是否换了归属"）。
- `countableTickets`：落在可用时段内、且不是 off-clock 的票据——利用率分子只用这个。

补录停业后回查会报告：受影响的摊位/场次、落入停业窗口的票据及其**未改变**的营业日归属
（含跨零点标记）、与本次记录重叠的停业、被显式登记取代的推导记录。

### 4. 停业登记的两种形态

- `registered`：起止时刻齐全，直接与可用窗口求差。
- `mirror-inferred`：登记只写了恢复营业时刻，结束时刻按"被覆盖摊位当天登记的收摊时刻"推导，
  并裁剪到当前场次内。显式登记可以通过 id 或时间重叠取代推导记录，避免同一段停业被扣两次。

作用范围支持 `stall` / `area` / `venue`；区域停业只影响当晚**本来在营业计划内**的摊位。

### 5. 时间处理

所有时刻统一转换为"浮动本地秒"（把 `Asia/Shanghai` 的墙上时间字段当作 UTC 重新解释），
区间运算因此是精确整数运算，结果与宿主机时区无关，测试可以直接比对秒数。

## 合成数据

- `data/venue.json`：7 天营业时间（周三至周六跨零点）、2 条日期覆盖（11-21 周年庆延时、11-24 年检提前收市）、
  3 个区域、10 个摊位（含按 `effective` 日期生效的排班变更）、4 条停业登记（含 1 条推导型）。
- `data/transactions.json`：602 张确定性生成的票据，其中 6 张专门复现边界情况：

| 票据 | 复现场景 |
| --- | --- |
| `TX-20261121-0597` | 11-21 00:15 售出，但归属 11-20 开市的营业日（跨零点不裂场） |
| `TX-20261119-0598` | 落在 11-19 停业窗口内（计入归属，不计入可经营票数） |
| `TX-20261118-0599` | 显式 `sessionId` 与时刻不一致（登记优先，标记 off-clock） |
| `TX-20261118-0600` | 时刻在全部营业日历之外（unallocated） |
| `TX-20261122-0601` | 恰好落在场次结束时刻（半开区间，排除） |
| `TX-20261121-9001` | 未知摊位（unallocated） |

重新生成：`node scripts/generate-transactions.mjs`（固定种子，可复现）。

## 目录

```
server.js               HTTP 入口：路由、静态文件、错误映射（ValidationError → 422）
lib/time.js             区间运算与时刻解析
lib/calendar.js         营业日历：按开市日期建场次、摊位窗口、跨零点解析
lib/closures.js         停业登记归一化、区间求差、推导停业、影响回查
lib/ledger.js           票据归属
lib/venue.js            分析主编排：逐场逐摊求交、票数统计、按晚序列
lib/validate.js         输入校验（问题列表 + 422）
lib/report.js           面向浏览器的序列化
lib/service.js          服务层：运行分析、补录停业、修订历史
data/                   登记表与合成票据
public/                 页面（原生 ES module，无构建步骤）
test/                   node --test 用例
```

## HTTP 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/state?from&to` | 登记表、场次、当前停业记录、默认窗口 |
| GET/POST | `/api/analysis?from&to` | 原营业分析 |
| GET/POST | `/api/availability?from&to` | 可用时段分母 |
| POST | `/api/closures/backfill` | 补录停业并回查；成功 201，校验失败 422 并带 `problems` |
| GET | `/api/sessions?from&to` | 场次列表 |

窗口为左闭右开 `[from, to)`，按营业日（开市日期）筛选；跨零点的场次整体保留，不会被窗口切成两半。
